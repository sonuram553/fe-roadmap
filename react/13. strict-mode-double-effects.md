# Why StrictMode runs effects twice

In development, with `<StrictMode>` on, React runs every effect, then its cleanup, then the effect again, straight away on first load. In a production build each effect runs once. This note is about why React does that on purpose, and what it is telling you when something breaks.

## 1. A fire drill

Think of `StrictMode` as a **fire drill**. A real fire is rare, and it always happens at the worst moment. So a building practises: everyone leaves and comes back in, on a quiet afternoon, while someone watches. If a door is blocked or a room never empties, you find out during the drill and not during the fire.

For a component, the "fire" is being switched off and switched back on again. The drill is React doing exactly that immediately after the first mount, while you are looking at it in development.

## 2. Why React expects effects to be switched off and on

React assumes it may need to turn a component's effects off and back on at any time. In real apps that happens constantly:

- the user navigates away from a page and comes back
- a component sits behind a condition (`{open && <Panel />}`) and is hidden and shown again
- a list item's `key` changes, so React throws the old one away and builds a new one
- you save a file in development and Fast Refresh swaps the component in place
- React 19.2's `<Activity mode="hidden">` hides part of the screen but keeps its state. While hidden, React runs the effects' cleanups, and when it is shown again it runs their setups again.

Every one of these comes down to the same order of events: **setup → cleanup → setup**. An effect is correct if that order leaves the app in the same state as a single setup. If the cleanup is missing or incomplete, each repeat leaves something behind: a second editor, a duplicate event listener, a second WebSocket, an interval that keeps firing.

These bugs are nasty because they only appear after the user has done something a few times, and then they pile up. The drill forces the repeat on first load, so a broken effect shows itself immediately. If your effect is correct, you cannot tell the drill happened.

## 3. Seeing it happen

Priya wraps the Monaco code editor in a component (see [lesson 11 of the Monaco series](../libraries/monaco/11-monaco-in-react.md)). Her first version creates the editor in an effect and never cleans it up:

```jsx
function NaiveEditor() {
  const boxRef = useRef(null);
  useEffect(() => {
    monaco.editor.create(boxRef.current, { value: 'SELECT 1;', language: 'sql' });
  }, []);
  return <div ref={boxRef} className="box" />;
}
```

She puts it next to a fixed version and runs both in a small demo, [react-strictmode-demo](../libraries/monaco/practice/react-strictmode-demo/), with a button that unmounts and remounts both components and a live count of editors on the page.

With `StrictMode` on, the naive component's box held **two** editors stacked on top of each other as soon as the page loaded, and the console said:

```
Element already has context attribute: box
```

The effect ran, nothing undid it, and the effect ran again into the same element. Monaco noticed its own markings were already there.

Then she removed `<StrictMode>` to see whether the drill was the cause. The box showed one editor, which looked fine. But clicking unmount and mount a few times told the real story. The number of editors alive on the page went:

```
2 → 1 → 3 → 2 → 4
```

Each cycle left one more editor behind, attached to a box that was no longer on the page. The bug was there all along. Without the drill it just waited until the user had clicked around.

## 4. The fix is a cleanup, not a guard

The fix is to make the cleanup undo exactly what the setup did:

```jsx
useEffect(() => {
  const editor = monaco.editor.create(boxRef.current, { value: 'SELECT 1;', language: 'sql' });
  return () => editor.dispose();
}, []);
```

With that, the drill creates an editor, disposes it, and creates another, leaving exactly one. Every remount does the same.

A common "fix" found online stops the second run with a flag instead:

```jsx
const didInit = useRef(false);
useEffect(() => {
  if (didInit.current) return;   // don't do this
  didInit.current = true;
  monaco.editor.create(boxRef.current, { value: 'SELECT 1;', language: 'sql' });
}, []);
```

That silences the drill without fixing the building. The editor is still never disposed, so it still leaks on every real unmount. Blocking the fire exit doesn't make the fire go away; it just means nobody notices the exit is blocked.

## 5. The other half: rendering twice

StrictMode also **calls your component function twice** on each render in development, and throws away one of the results. That checks a different rule: rendering must be pure. The component function should only calculate JSX from props and state. It should not change a global variable, start a request, or create an editor. A pure function gives the same answer twice, so the double call is invisible. One with side effects does them twice, and you notice.

Side effects belong in effects (or event handlers). Effects get the setup-cleanup-setup drill from §2, and rendering gets the call-it-twice check.
